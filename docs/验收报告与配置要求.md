## 2. 验收判定规则

每一项只能记录为以下之一：

- **通过**：操作成功，页面结果正确；刷新/重新进入后数据仍在；需要外部系统时完成外部回读。
- **部分通过**：展示或接口成功，但持久化、队列、桌面端或外部回读未完成。
- **阻塞**：前置条件缺失、登录失败、接口不可达、凭据无效或结果错误。
- **不适用**：必须写明原因，不能用来掩盖未测。

验收证据至少包含：执行时间、环境/域名、账号角色、操作截图、请求或任务编号、数据库/队列/企业微信回读结果、异常日志（如有）。敏感信息只记录“已配置/末四位”，不记录密码和完整密钥。

## 3. 配置要求

### 3.1 服务器与部署

| 配置项 | 要求 | 验证方式 |
|---|---|---|
| 域名与 HTTPS | 使用最终业务域名；证书有效；HTTP 重定向 HTTPS | 浏览器首页、证书有效期、`curl -I` |
| Docker | Docker Engine 与 Compose v2；db、redis、backend、frontend、edge 均为 `Up` | `docker compose ps` |
| 入口路由 | `/` 返回前端 HTML；`/api/`、`/admin/api/` 转后端；`/ws/` 支持 WebSocket；下载路径可访问 | 浏览器 + HTTP/WebSocket 探针 |
| 数据库 | MariaDB 11.4 或兼容版本，utf8mb4；使用独立生产库和最小权限账号 | 登录后健康页、数据库连接、迁移版本 |
| Redis | Redis 7.x，开启持久化；仅内网可达 | 健康页、重启后队列状态 |
| 持久化卷 | 数据库、Redis、上传文件、桌面版本文件均使用持久卷 | 重启容器后抽查文件和记录 |
| 备份 | 每日数据库备份；至少完成一次恢复演练；备份文件不可直接暴露公网 | 备份日志、恢复后的行数/校验和 |
| 文件上传 | 生产上限与 Nginx、Spring 配置一致；验证大文件失败时提示清楚 | 合法文件、超限文件各一次 |
| 时间 | 服务器、数据库、浏览器统一 Asia/Shanghai 或明确记录时区 | 任务时间、公告排期、审计时间 |

### 3.2 环境变量与安全

从 `deployment/.env.example` 复制并逐项替换 `CHANGE_ME`。生产必须设置：`DB_NAME`、`DB_USER`、`DB_PASSWORD`、`MYSQL_ROOT_PASSWORD`、长度至少 64 的 `SYSTEM_JWT_SECRET`、`MOCK_EXTERNALS=false`、`PDA_DOMAIN`、`PDA_HTTP_PORT`、`MAX_FILE_SIZE`、`VITE_DEFAULT_API_BASE_URL`。

禁止事项：把真实密钥提交 Git；沿用默认密码；把本地客户、聊天、预约、映射、账号或历史配置直接导入所谓“干净生产库”；用 `MOCK_EXTERNALS=true` 的结果宣称真实外部验收通过。

### 3.3 账号与权限

先保留一个可用管理员，再建立测试账号：`ADMIN`、`LEADER`、`KEEPER` 各 1 个。为每个账号记录角色、所属组、直属组长和测试手机号。验收后删除临时账号，保留正式账号。

必须验证：管理员可配置；组长可查看授权范围和监督记录；员工只能操作授权范围；停用账号立即不能登录；重置密码后旧密码失效；退出登录后浏览器返回登录页且受保护 API 返回未授权。

### 3.4 企业微信与三张表

推荐使用服务器转发（`WECOM_TRANSPORT_MODE=RELAY`），填写服务器转发地址、`WECOM_RELAY_KEY_ID`、`WECOM_RELAY_SECRET`。只有服务器出口 IP 已加入指定企业微信应用可信 IP 时，才使用 `DIRECT`，并填写企业 ID 与应用 Secret。

必须准备并确认以下表及字段归属：

1. **客户主表**：唯一客户事实来源，至少有稳定唯一字段（通常手机号）和客户档案字段。
2. **分配表**：负责员工、组、门店、线索来源、分配状态等分配字段。
3. **到店表**：预约、到店状态、到店资料和体验结果；预约事实不臆造到客户主表不存在的字段。

在系统中分别保存文档/子表 ID、视图 ID、源表标识、唯一字段标题和字段映射。保存后必须重新读取并核对：页面选择的数据源、数据库保存的数据源 ID、请求使用的数据源 ID 三者一致。

### 3.5 AI、Skill、识图和 LLM

至少准备一个真实可用的 Skill 环境、识图环境和 LLM 环境，协议为 OpenAI Compatible 或系统明确支持的协议。LLM 至少配置以下业务场景路由：回复生成、档案提取、跟进建议、异常识别、总结补位；每个场景明确优先级、启用状态、超时、模型和降级策略。

验收前准备：真实 Base URL、API Key、模型名、超时和限流说明；一组可脱敏聊天截图；一条可识别文字消息；一组企业红线、标签和降级回复。

### 3.6 内容、规则与治理

准备最小可验收数据：普通开场话术、团购话术、到店提醒、知识片段、门店定位、小程序引导各 1 条；标签分类至少 2 个（单选和多选各 1），每类至少 2 个值；跟进规则至少 1 条提醒规则和 1 条通知组长规则；公告准备立即发布、定时发布、停止各 1 条。

## 4. 登录与系统前置验收（P0）

1. 浏览器打开最终域名根路径，返回前端页面；访问 `#/admin` 能显示登录页。
2. 使用管理员登录，记录脱敏后的登录响应和时间；访问受保护健康接口返回成功。
3. 刷新页面、关闭重开浏览器，仍能按设计保持或恢复会话。
4. 退出登录，再访问后台 API 必须返回未授权；使用停用账号登录必须失败。
5. 服务器重启或重启容器后，管理员、配置和测试数据仍存在。

登录任一步失败，后续板块只允许做静态检查，不得记录为通过。

## 7. 外部系统与数据一致性验收

必须分别证明以下链路，而不是只看 HTTP 200：

`桌面端/浏览器 → API → MariaDB → Redis/队列 → 企业微信转发或官方 API → 指定表行回读`

企业微信写回至少记录：表名、行 ID、唯一手机号、写入字段、写入值、写入时间、relay/API 响应（脱敏）。客户主表、分配表、到店表要逐表回读；“表存在”不等于“来源和路由正确”。

## 8. 回归、容量与安全

- 重复点击保存、刷新、重新登录、浏览器后退，不产生重复记录或重复写回。
- 必填字段为空、非法日期、错误手机号、错误文件类型、超大文件均有可理解提示。
- 并发至少覆盖 5 个员工；记录 P95 响应时间、队列等待、识图和模型耗时。
- 检查越权、停用账号、过期 Token、CSRF/跨域策略、上传文件访问权限和日志脱敏。
- Docker/服务器重启后重复执行 DSK-04、DSK-06、DSK-07 的查询和回读。

## 10. 最终放行门槛

只有同时满足以下条件，才能写“验收通过/可投入使用”：

1. P0 登录、权限、路由、数据库、Redis、备份恢复全部通过。
2. A～N 每个板块都有通过记录，没有未解释的部分通过。
3. DSK-01～DSK-10 中与实际业务相关的场景全部通过，至少一条从桌面端到企业微信表回读的链路通过。
4. `MOCK_EXTERNALS=false`，真实 Skill、识图、LLM 和企业微信连接均有新鲜证据。
5. 生产安装包签名、版本发布/撤回和下载验证通过。
6. 所有阻塞项有关闭证据；只要登录仍不可用，最终结论必须保持“未验收/阻塞”。
