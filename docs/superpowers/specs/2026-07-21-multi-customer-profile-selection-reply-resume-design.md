# 多客户档案确认与回复续跑设计

## 目标

修正截图识别主线中“匹配到多个客户时，后台提前使用第一个候选客户生成回复”的问题。

修改后的主线必须满足：识图和客户匹配完成后，如果只有一个客户则直接继续；如果没有档案则生成不依赖客户档案的通用回复；如果有多个客户则保存任务、立即提醒员工、允许逐个查看完整档案，只有员工明确确认后才读取该客户档案并调用 Skill 和回复 LLM。员工暂时不处理或关闭桌面端时，任务不得丢失。

## 当前问题

当前代码的多客户路径存在以下差异：

1. `ChatOrchestrationService.recognize()` 在匹配结果为多个客户时仍调用 `firstCustomer(match)`，随后进入 Skill 和回复 LLM。
2. 桌面端收到多个候选后只把回复会话暂停在候选状态，候选确认并没有形成可靠的后端续跑闭环。
3. 打开候选客户档案和确认该客户是当前聊天对象没有严格分开，员工不能安全地逐个查看后再决定。
4. 前端虽然会把部分回复会话写入本机 `localStorage`，但它不是跨重启、跨异常和后端恢复的可靠任务来源。
5. 员工忘记处理时，没有完整的持续提醒、任务恢复和选择后自动继续生成机制。

## 已确认的业务流程

```text
员工点击识别聊天
  -> 系统截取当前聊天窗口
  -> 图片 LLM 识别平台、昵称、手机号、平台标识和聊天内容
  -> 系统查找客户档案
     -> 只有一个客户：读取档案 -> Skill -> 回复 LLM -> 展示回复
     -> 没有客户档案：无档案模式 -> Skill -> 回复 LLM -> 展示通用回复
     -> 有多个客户：保存待选择任务 -> 立即提醒员工 -> 展示候选列表
        -> 员工点击“查看档案”：只预览完整档案，不生成回复
        -> 员工返回并查看其他候选：任务继续等待
        -> 员工点击“确认是此客户”：读取最新档案 -> Skill -> 回复 LLM -> 展示回复
        -> 员工暂时不处理或关闭软件：任务持续保留，重新打开后继续提醒
```

“暂停”只暂停该任务的个性化回复生成，不阻塞桌面端，也不占用一个持续运行的 LLM 请求。

## 核心设计

### 后端是待处理任务的唯一真实来源

新增数据库持久化的回复任务。数据库保存任务状态，桌面端本地状态只用于加快显示，不能决定任务是否存在或是否完成。

多客户匹配完成时，后端保存以下继续执行所需的信息：

- 任务编号和所属员工账号。
- 识别来源和非敏感捕获方式。
- 识别出的平台、昵称、手机号和平台客户标识。
- 已提取的聊天消息和用于生成回复的客户话语。
- 候选客户的手机号标识。
- 创建时间、更新时间、失效时间和当前状态。

禁止保存原始截图。图片 LLM 返回结构化识别结果后，原始图片立即释放，继续遵守项目“图片不存储”的既有决策。

候选客户的完整档案不复制进任务表。员工查看候选档案时，系统仍通过现有客户档案接口读取最新数据，避免任务保存期间档案已经变化。

### 任务状态

任务使用以下状态：

| 状态 | 含义 | 可进入的下一状态 |
|---|---|---|
| `WAITING_CUSTOMER` | 等待员工确认客户 | `GENERATING`、`CANCELLED`、`EXPIRED` |
| `GENERATING` | 已确认客户，正在生成回复 | `READY`、`FAILED` |
| `READY` | 回复已生成，可展示 | 完成态 |
| `FAILED` | 生成失败，可由员工重试 | `GENERATING`、`CANCELLED`、`EXPIRED` |
| `CANCELLED` | 员工明确放弃 | 完成态 |
| `EXPIRED` | 超过 24 小时未处理 | 完成态，必须重新识别 |

同一个任务只能有一次有效生成过程。重复点击确认、网络重试或两个窗口同时操作时，后端必须通过状态条件更新保证不会重复调用 Skill 和回复 LLM。

如果服务在 `GENERATING` 状态中断，恢复任务会把超过生成时限且没有结果的任务改为 `FAILED`，允许员工重新生成，不能永久卡在“正在生成”。

### 识别接口行为

现有 `POST /api/v1/chat/recognize` 保留为统一入口：

- 唯一客户：保持原主线，直接返回生成后的回复。
- 无档案：保持无档案主线，直接返回通用回复。
- 多个客户：不得调用 Skill 和回复 LLM；创建待选择任务，返回任务编号、任务状态和候选摘要，回复建议为空。

多客户识别响应返回后，桌面端必须停止“正在生成回复”的进度展示，改为明确的“需要选择客户”。

### 待处理任务接口

新增以下接口职责，最终字段名和错误码需要同步写入 `SHARED_CONTRACTS.md`：

- 查询当前员工未完成的回复任务，用于登录、启动、重连和手动刷新后的恢复。
- 查询单个任务状态和结果，用于确认请求超时后判断后台是否已经完成。
- 确认候选客户，校验任务归属、任务状态、有效期、客户访问权限以及所选客户是否属于原候选集合。
- 重试生成失败的任务。
- 主动取消待选择任务。

确认接口只有在所有校验通过后才能把任务从 `WAITING_CUSTOMER` 改为 `GENERATING`。选择成功后读取该客户的最新档案，再按原始截图识别场景调用 Skill 和回复 LLM，不能改成档案卡主动回复场景。

### 候选列表与档案预览

识别到多个客户后，桌面端立即执行以下动作：

1. 把助手窗口带到用户可见位置并打开“请选择对应客户”界面。
2. 候选列表展示昵称、手机号后四位、客户来源、客户类型、当前阶段、负责员工、意向门店或项目、最近跟进时间。
3. 每个候选提供“查看档案”，点击后加载现有完整档案视图。
4. 查看档案不会改变任务状态，也不会调用 Skill 或回复 LLM。
5. 档案视图提供明确的“确认是此客户”命令，同时允许返回候选列表继续查看其他客户。
6. 只有“确认是此客户”才调用后端确认接口。

不能把点击候选行、打开档案、切换档案或关闭预览解释为确认客户。

### 提醒与恢复

员工没有立即选择时：

- 回复面板保留“待选择客户”任务和候选入口。
- 侧边栏持续显示未处理数量，不使用自动消失的提示代替持久状态。
- 桌面端不在前台时发送一次系统桌面提醒，点击提醒直接打开对应候选列表。
- 桌面端重新启动、重新登录或网络重连后，从后端重新加载未完成任务。
- 本机缓存只能用于先显示旧状态，后端返回后必须以服务端结果覆盖。
- 任务完成、取消或过期后移除待处理提醒。

提醒不能替员工自动选择第一个候选，也不能因为提醒超时而自动生成回复。

### 生成完成与失败

确认客户后，原回复会话进入“正在生成回复”，并保持原识别任务的会话编号，避免结果出现在错误的回复卡片中。

生成成功后：

- 保存最终回复和回复来源。
- 把任务状态改为 `READY`。
- 在原回复会话中展示建议。
- 清除该任务的待选择提醒。
- 如果桌面端不在前台，发送“回复已生成”的桌面提醒。

生成失败后：

- 把任务状态改为 `FAILED`，保存公开错误码，不保存密钥或内部提示词。
- 保留员工已经确认的客户。
- 提供“重新生成”和“取消任务”。
- 重试时不得重新识图，也不得要求员工重新选择客户，除非该客户档案已经删除或员工失去访问权限。

如果候选档案已删除、超出员工权限或不再有效，确认失败并返回候选列表，刷新可访问候选，严禁退回到自动选择第一位。

## 数据边界与隐私

- 不保存原始截图、图片 Base64 或截图文件路径。
- 只保存继续生成所必需的结构化识别文本。
- 任务按员工账号隔离，不能读取或确认其他员工的任务。
- 客户档案仍走现有访问权限检查。
- 日志只记录任务编号、状态、阶段耗时、错误码和非敏感识别来源，不记录完整聊天文本、档案内容、提示词或密钥。
- 任务到期后清除可恢复的聊天上下文；审计记录只保留非敏感状态信息。

## 不在本次范围

- 不改变图片 LLM 的识别提示词和客户匹配算法。
- 不重做客户档案页面。
- 不改变 Skill 的业务方向判断。
- 不自动点击聊天软件或自动发送消息。
- 不把“复制回复”当成“确认已发送”。
- 不顺带解决截图超时、捕获来源丢失或复制触发发送副作用；这些问题单独处理，避免扩大本次修改。

## 测试与验收

### 后端自动化测试

- 多客户匹配时不调用 Skill 和回复 LLM，并创建 `WAITING_CUSTOMER` 任务。
- 唯一客户和无档案路径保持现有行为。
- 只有任务所属员工能读取、确认、重试和取消。
- 所选客户必须属于原候选集合并通过客户访问权限检查。
- 确认后使用原识别聊天内容和所选客户最新档案生成回复。
- 重复确认只生成一次。
- 生成成功、失败、重试、取消、过期和服务中断恢复的状态转换正确。
- 原始截图不会写入数据库、Redis、文件或日志。

### 桌面端自动化测试

- 多客户响应显示持久待选择状态，不显示错误客户的回复。
- 候选列表立即可见，助手窗口和提醒可打开对应任务。
- 点击“查看档案”只加载档案，不确认客户、不发起生成。
- 点击“确认是此客户”后在原会话中自动继续生成。
- 可以返回并查看其他候选。
- 重启、重新登录和网络重连后恢复未完成任务。
- 重复点击确认不会创建重复生成请求。
- 任务完成、取消和过期后正确清除提醒。

### 真实人工验收

使用真实微信、企业微信和抖音网页截图分别验证：

1. 唯一客户直接生成回复。
2. 两个同昵称客户时不会提前生成回复。
3. 可以查看两个候选的完整档案，查看行为不等于确认。
4. 确认第二个客户后，Skill 和回复 LLM 使用第二个客户档案。
5. 关闭并重启桌面端后，待选择任务仍在。
6. 忘记处理后侧边栏持续提示，点击提示回到正确任务。
7. 选择后离开助手窗口，回复完成时收到提醒并能打开正确会话。
8. 任务超过 24 小时后不可继续使用旧聊天内容，提示重新识别。

## 实施防跑偏规则

后续实施必须遵守：

1. 先写证明当前错误行为的失败测试，再改生产代码。
2. 后端先完成“不提前生成”和持久任务，再接桌面端；不能先用前端隐藏错误结果冒充修复。
3. 数据库是待处理任务的唯一真实来源，不能只依赖 `localStorage` 或 Redis。
4. “查看档案”和“确认客户”必须是两个独立动作。
5. 选择后必须沿原截图识别会话自动续跑，不能要求员工再点一次“生成回复”。
6. 不保存原始截图，不扩大到其他主线缺陷。
7. 每完成一个实施步骤，更新实施任务清单中的状态、测试命令和最新证据。
8. 上下文压缩或会话中断后，先读取本设计文档、实施计划、任务清单、当前 Git 状态和最近测试报告，再从第一个未完成步骤继续；不得根据聊天记忆重新设计。
